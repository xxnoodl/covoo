# M2 Wi-Fi transport

Implementation added. Final CI verification and physical acceptance are pending.
M1 capture, clarity and five-minute stability passed on 2026-10-26. M3 hasn't started.

## Product name

The product name is `covoo`, replacing the working name PhoneMic.
Applied to the iPhone home-screen name, app title, Windows receiver greeting,
mDNS advertisement and distributed artifact names. Naming remains configurable.
Internal target/package names can stay unchanged where renaming has no user benefit.
Keep historical test reports accurate about the builds that were tested.

## Scope

Discovery, secure pairing, separate control and audio channels, Wi-Fi streaming,
Windows reception, packet diagnostics and reconnection. Physical validation must
confirm microphone audio reaches Windows and PCM continuity is intact.
No driver, ASIO, USB transport or Android implementation in this milestone.

## Implementation Summary

Encrypted LAN audio from native capture to a Windows WAV receiver. Includes
Bonjour discovery, QR/link pairing, TLS 1.3 control, authenticated UDP PCM,
heartbeats, control RTT, bounded network queues, reconnection and per-stream
WAV/JSON/CSV output. Phone capture keeps a local reference recording.

## Architecture Changes

`audio-transport` owns control framing, TLS identity and AEAD/replay contracts.
Swift uses Network.framework/CryptoKit with matching fixtures. Capture submits
PCM to a separate C SPSC queue; networking stays outside RemoteIO. Windows
separates UDP authentication, bounded delivery and file assembly. See
[transport decision](../decisions/0003-secure-lan.md) and
[security model](../security/m2-threat-model.md).

## Files Changed

- `crates/audio-transport`: control framing, TLS setup, token validation, AEAD,
  replay window, fixtures and crypto benchmark.
- `crates/windows-receiver`: CLI, pairing QR, mDNS, control/UDP receiver, bounded
  reordering, recordings and synthetic loopback tests.
- `apps/ios/Sources`: discovery, pinned TLS, bounded encrypted sender, capture
  integration and connection diagnostics. Project plist adds LAN/Bonjour and URL declarations.
- `apps/ios/Tests`, `tests/interoperability`: shared crypto fixture, actual
  Swift-to-Rust TLS/UDP test and recording comparison tests.
- `scripts`: Windows launcher, Swift network test and byte-exact PCM comparison.
- CI packages `covoo-windows-x64` and `covoo-ios-sideload-package`.

## Verification

Local Windows commands:

```powershell
powershell -File scripts/verify.ps1
python -m unittest discover -s tests/interoperability -p test_compare_recordings.py
cargo run --release --locked -p audio-transport --example crypto_bench
```

Rust formatting, Clippy with warnings denied, 16 Rust tests, three Python tests,
release build and CLI smoke run passed. A Windows accepted-socket nonblocking
issue found by the first loopback test was fixed; the encrypted loopback now
checks exact PCM, 48/44.1 kHz formats, certificate/token rejection, replay/tamper
rejection, key rotation and reconnects. Recorder tests cover reordering, loss,
late delivery, missing tails, sudden disconnect and bounded large gaps/storage.

[Initial CI](https://github.com/xxnoodl/covoo/actions/runs/40300152631) passed for
`2c3b937`: Windows/Linux Rust, native sanitizers, unsigned iOS simulator/device
builds, three simulator tests, and a real Network.framework-to-Rust loopback.
That loopback delivered 200 encrypted packets with all 48,000 PCM samples exact.
Follow-up fault/report hardening and explicit Swift wrong-pin rejection await final CI.

At `2c3b937`, local Windows release AEAD seal+open for 1000-byte plaintext measured
p50 4.40 us, p95 5.50 us and p99 20.30 us after warm-up. This is a software
microbenchmark, not Wi-Fi/input latency or an iPhone CPU measurement.

## Hardware Validation

No M2 iPhone-to-Windows LAN, discovery, pairing QR, interruption or end-to-end
latency test has occurred. The Mac loopback exercises matching APIs/bytes but
isn't an iOS hardware test. M1's local recording result remains separate evidence.

## Known Limitations

- Foreground recording only; no PC monitoring or Windows microphone endpoint.
- Bounded file reordering only. No playback clock, ASRC or drift correction yet.
- Pairing is process-scoped and not saved on the phone. Restarting the receiver
  changes its identity/token and requires a new QR. No installed root certificate.
- Discovery/firewall/router behavior requires physical testing; manual host override exists.
- Lost audio isn't retransmitted. Short gaps insert counted silence; gaps beyond
  two seconds omit counted frames. Leading/trailing loss is reported explicitly.
- Disconnects create new stream/key/file segments. Continuity through outages isn't claimed.
- Sender queue limit/stale drops and control RTT aren't measured input latency.
- No external security audit. The local pairing HTML contains a bearer credential.
- Abrupt receiver termination can leave a WAV header unfinished; stop from the phone first.
