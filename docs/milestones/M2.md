# M2 Wi-Fi transport

Implementation added. Physical acceptance is pending.
M1 capture, clarity and five-minute stability passed on 2026-10-26. M3 hasn't started.

## Product name

The product name is `covoo`, replacing the working name PhoneMic.
Applied to the iPhone home-screen name, app title, Windows receiver greeting,
mDNS advertisement and distributed artifact names. Naming remains configurable.
Internal target/package names can stay unchanged where renaming has no user benefit.
Keep historical test reports accurate about the builds that were tested.

## Scope

Discovery, secure pairing, separate control and audio channels, Wi-Fi streaming,
Windows reception, packet diagnostics and reconnection. Physical validation must
confirm microphone audio reaches Windows and PCM continuity is intact.
No driver, ASIO, USB transport or Android implementation in this milestone.

## Implementation Summary

Encrypted LAN audio from native capture to a Windows WAV receiver. Includes
Bonjour discovery, QR/link pairing, TLS 1.3 control, authenticated UDP PCM,
heartbeats, control RTT, bounded network queues, reconnection and per-stream
WAV/JSON/CSV output. Phone capture keeps a local reference recording.

## Architecture Changes

`audio-transport` owns control framing, TLS identity and AEAD/replay contracts.
Swift uses Network.framework/CryptoKit with matching fixtures. Capture submits
PCM to a separate C SPSC queue; networking stays outside RemoteIO. Windows
separates UDP authentication, bounded delivery and file assembly. See
[transport decision](../decisions/0003-secure-lan.md) and
[security model](../security/m2-threat-model.md).

### Follow-up receiver changes

The original CSV shows 26.721, 23.837, 32.5629 and 31.3396 ms between the received
packets surrounding the four holes. This doesn't distinguish router/radio loss
from host socket overflow. The old combined replay counter can't establish
whether its 62 entries were duplicates, stale traffic or forged counters.

The follow-up receiver requests a bounded 256 KiB per-socket UDP receive buffer
and prints/reports the actual OS value. This provides burst headroom; it isn't
a jitter-buffer target, latency measurement or proof that packet loss is fixed.
No system-wide network/security setting changes. Safe `socket2::SockRef` wraps
the documented [SO_RCVBUF option](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-setsockopt);
no application unsafe Rust was added.

Replay checks retain the 128-packet window but authenticate before classifying
rejections. `authenticated_duplicates` counts already-seen in-window counters;
`authenticated_too_old` counts valid packets outside the window, which may include
very old duplicates. Their sum remains `replay_rejected` for compatibility.
Invalid tags count as rejected datagrams, even when their counter looks duplicated.
Reports include out-of-order count, largest forward counter gap, maximum interval
between valid new arrivals, actual receive buffer size and the first 32 packet
events. A forward gap can still be filled by reordering; it isn't confirmed loss.
Diagnostics contain no credentials or PCM and remain bounded.

### Packet protection experiment

User subsequently reported switching apps and restarting recordings. Current
capture observes `didEnterBackgroundNotification` and stops with a report event;
background recording isn't enabled. The matched 339.27-second take reports
"Stopped", a valid full sender summary and no reconnects. The other PC segment
wasn't attributed to a phone export. Switching explains separate sessions, but
doesn't establish the cause of isolated holes within the matched take.

Optional sender protection schedules one existing encrypted packet copy 5 ms
later, discarding copies older than 15 ms. Eight pending copies and eight
in-flight sends bound storage; at most four send slots dispatch copies at once.
Originals aren't deliberately delayed. Stop waits for copies or counts skips on
timeout. Failure/reconnection discards pending old-key copies. Phone UI has a
toggle before connecting plus backup/skip counters. Reports distinguish unique
packets, redundant sends and total bytes. Wire format/receiver rules are unchanged.
A new iPhone build is required; the previous diagnostic PC receiver is compatible.

Traffic roughly doubles and may worsen congestion. Loss of both copies remains
unrecoverable; no physical latency target or root cause is claimed. See the
updated transport decision/security model for bounds and cryptographic treatment.

Expanded Rust TLS/UDP tests deliberately drop first, middle and last primaries:
delayed copies restore bit-exact PCM with continuity true. A separate case loses
both copies of one packet and verifies counted silence and continuity false.
Swift tests cover timing, expiry, capacity and deterministic primary loss. CI
must execute them because Swift/Xcode isn't available on this Windows machine.
The real Swift-to-Rust network test now checks backup accounting and receiver
duplicates as well as every PCM sample. Protected-stream hardware testing remains
pending; M3 remains blocked on physical acceptance.

## Known Limitations

- Foreground recording only; no PC monitoring or Windows microphone endpoint.
- Bounded file reordering only. No playback clock, ASRC or drift correction yet.
- Pairing is process-scoped and not saved on the phone. Restarting the receiver
  changes its identity/token and requires a new QR. No installed root certificate.
- Discovery/firewall/router behavior requires physical testing; manual host override exists.
- Initial pairing and receiver binding support IPv4 only.
- Lost audio isn't retransmitted. Short gaps insert counted silence; gaps beyond
  two seconds omit counted frames. Leading/trailing loss is reported explicitly.
- Disconnects create new stream/key/file segments. Continuity through outages isn't claimed.
- Sender queue limit/stale drops and control RTT aren't measured input latency.
- No external security audit. The local pairing HTML contains a bearer credential.
- Abrupt receiver termination can leave a WAV header unfinished; stop from the phone first.
