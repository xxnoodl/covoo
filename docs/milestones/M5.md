# M5 Latency and clocks

Status: shared clock correction and diagnostic tooling implemented; physical
acceptance and ASIO feasibility decisions pending. No ASIO code is implemented.

Desktop latency profiles and an independent dry PC monitor are now implemented.
The November 2 Ableton log still reports 106 ms driver I/O; Live-effect latency
is not fixed by bypassing its dry monitoring path. See
[the Ableton monitoring update](ableton-latency-update.md) for evidence and limits.

## Implementation and architecture

Existing playback uses bounded queues and sinc ASRC with occupancy feedback,
bounded ratio adjustment and explicit recovery counters. The native low-period
backend reports the actual Windows engine period. New fixed-size starvation
events distinguish initial buffering from recovery silence.

The offline `replay_playout` example now accepts a synthetic output-clock offset
in ppm, rejects nonfinite/out-of-range offsets and models clock speed separately
from packet arrival times. This uses the production Renderer, without a Windows
endpoint. It does not estimate a phone clock from cross-device timestamps.

```powershell
cargo run -p windows-receiver --example replay_playout --release --locked -- RECEIVER.csv 200
cargo run -p windows-receiver --example replay_playout --release --locked -- RECEIVER.csv -200
```

Input is a contiguous, ordered 48 kHz receiver trace. Test signals are constant
queue-demand samples; this is not an audio fidelity or hardware performance test.
See [the investigation](../performance/latency-investigation.md) for model limits
and the common-reference physical latency method.

## Files and verification

Important files: `playout.rs`, `native_output.rs`, `live.rs`,
`examples/replay_playout.rs` and `scripts/latency-audit.py`. Automated tests cover
tone preservation with independent clocks, bounded recovery, synthetic-clock
direction, ingress integrity and malformed traces. Physical latency stays null.
Local full verification and +/-200 ppm trace replays are run for this batch.
CI results are recorded in the implementation batch report when available.

Local synthetic-clock replays of receiver `1e83da3c4bd2f87e` completed all
16 buffer/phase cases for each offset: +200 ppm produced 0..20 underruns and
-200 ppm produced 0..14. No conclusion about real phone/output drift follows
from these injected offsets. The model continues to report physical latency null.

## Hardware and known limitations

The user heard improved monitoring and a clear 8 ms take. Reported source
underruns still occurred. No physically calibrated full monitoring delay,
60-minute clock stability or high-load scheduling result exists. Native queue
capacity is not latency. Reducing upstream buffering cannot guarantee removal of
downstream cable/DAW/output delay.

## Next steps and required user actions

No new recording now. Batched physical tests are in `todo.md`. ASIO SDK licensing,
WASAPI playback compatibility and clock/latency reporting require a separate
feasibility decision before an approved prototype. Do not aggregate drivers or
claim generic ASIO interoperability. M5 is not accepted yet.

## Headphone investigation update

Native output now samples IAudioClock position/QPC at most four times a second,
using the device's reported frequency rather than assuming positions are frames.
Reports distinguish unavailable/invalid estimates, clock query errors and ASRC
minimum/maximum correction over the take. Final zero correction alone no longer
hides earlier adjustment. No value represents physical pitch or end-to-end delay.

Native shutdown now calls Reset only after successful Stop, before releasing
the client. Any failure is reported. This flushes this client stream; it is not
a system-device reset and is not claimed to fix the EarPods symptom. The direct
headphone launcher defaults to the existing legacy backend for a later explicit
compatibility comparison. DAW routing defaults/settings and OS audio settings
are unchanged. No physical headphone test was run for this update.

Sources: [Microsoft Reset](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-reset),
[device position/QPC units](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition).
